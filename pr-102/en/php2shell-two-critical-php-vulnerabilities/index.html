PHP2Shell: Two Critical PHP Vulnerabilities and What to Do Now

Two critical vulnerabilities in the PHP runtime itself were disclosed on October 21, 2026: CVE-2026-109618 and CVE-2026-109619, nicknamed “PHP2Shell.” Both are rated CVSS 9.2 (v4.0), and both can expose applications to unauthenticated remote code execution and memory disclosure.

This is not a bug in a framework or a plugin. It is in PHP core, so it does not matter whether you run WordPress, Laravel, Symfony, Zend or a ten-year-old script.

What is affected

According to Google Cloud, “all versions of PHP from 5.4 through 8.5.11” are vulnerable. Fixes are in PHP 8.5.12, 8.4.27, 8.3.36 and 8.2.35. The PHP project is not releasing fixes for 8.1 or earlier, which have reached end of life.

That last point is the uncomfortable one: if you are on 8.1, 7.x or 5.x, there is no patch to apply. The only fix is upgrading to a supported branch.

How the flaws work (briefly)

Google Cloud describes them in one sentence each:

  • CVE-2026-109618: out-of-memory handling can interrupt PHP while internal request data is only partially initialized, and request cleanup may then treat the invalid data as valid.
  • CVE-2026-109619: request-owned internal state can survive after its backing memory has been freed, so a later request handled by the same worker may use stale state before normal initialization resets it.

Both are memory-lifecycle bugs in how PHP handles requests. The second one is a reminder that long-lived workers (PHP-FPM, for example) carry state from one request to the next, and a use-after-free there can cross request boundaries. Google also notes that mitigating circumstances can make exploitation harder; neither source describes the exploit path in detail.

What I would do today

  1. Find every PHP you run. php -v on servers, but also base images in your Dockerfiles, CI images, and anything a hosting provider manages for you. Containers are the usual blind spot.
  2. Upgrade to a patched release (8.2.35, 8.3.36, 8.4.27 or 8.5.12 or later) and redeploy. Updating a package on a host does nothing for an image that has already been built.
  3. Rebuild images. Pinned or cached base layers will keep serving the vulnerable version until you rebuild without cache.
  4. Plan the end-of-life migration. If you are on 8.1 or older, this is no longer a someday task.
  5. Restart long-lived workers. An updated binary on disk is irrelevant until PHP-FPM and friends are restarted.
  6. Check managed platforms. On Google Cloud, App Engine standard patches supported runtimes automatically, but App Engine flexible does not, and Cloud Run only updates automatically when automatic base image updates are enabled. Other providers will have their own rules; do not assume.
  7. Read the primary sources: the PHP advisory and the GitHub advisories for these CVEs, before acting on anyone’s summary, including this one.
