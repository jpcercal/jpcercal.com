PHP2Shell: Two Critical PHP Vulnerabilities and What to Do Now

João Paulo Cercal Two critical flaws in the PHP runtime, CVE-2026-109618 and CVE-2026-109619, can allow unauthenticated remote code execution. Here is what the advisories and public reports say, how a WAF and layered controls help, and how to patch PHP and your Docker images. https://staging.jpcercal.com/pr-102/en/php2shell-two-critical-php-vulnerabilities/index.svg https://staging.jpcercal.com/pr-102/en/php2shell-two-critical-php-vulnerabilities/index.dark.svg en post

  • Portuguese: PHP2Shell: Duas Vulnerabilidades Críticas no PHP e o Que Fazer Agora

Two critical vulnerabilities in the PHP runtime itself were disclosed on October 21, 2026: CVE-2026-109618 and CVE-2026-109619, nicknamed “PHP2Shell.” Both are rated CVSS 9.2 (v4.0) and both can lead to unauthenticated remote code execution. The disclosure was moved up from October 22 after the CVE IDs leaked on October 20 (PHP Foundation).

This is not a bug in a framework or a plugin. It is in PHP core, so it does not matter whether you run WordPress, Laravel, Symfony, Zend or a ten-year-old script.

I updated this post after reading the two GitHub security advisories, the PHP Foundation write-up and the vendor pages linked in the references.

The short version: update PHP to 8.5.12, 8.4.27, 8.3.36 or 8.2.35, restart every worker, and check the version that is actually running. A WAF can buy you time but it is not a patch. Below: how the flaws work, what a WAF and defense in depth can and cannot do (with a mitigation map and an Akamai example), how to patch PHP and the Docker images, how to verify, and the sources.

What is affected

The fixed releases are PHP 8.5.12, 8.4.27, 8.3.36 and 8.2.35. Both CVEs are fixed by the same releases. Anything older than those on the same branch is affected.

For older branches the sources differ, and this is the uncomfortable part:

  • The GitHub advisories (GHSA-w8hw-w9fx-j79w and GHSA-6wmf-4rv5-p3rp) list the 8.2 to 8.5 branches.
  • Google Cloud says “all versions of PHP from 5.4 through 8.5.11” are vulnerable (Google Cloud).
  • Upstream PHP ships no release for 8.1 or earlier. The security team did publish minimal source backports for 7.4, 8.0 and 8.1 as branches in php-src, for people who build from source and have no LTS vendor (links in the patching section).
  • Some vendors ship backported packages for older branches: Ubuntu lists fixed packages from 14.04 through 26.10 (the oldest releases via Ubuntu Pro), and Zend lists ZendPHP builds for 7.2, 7.3, 7.4 and 8.1. Zend’s page says the flaw affects all PHP 5, 7 and 8.0/8.1 versions (Ubuntu, Zend).

So if you are on 8.1, 7.x or 5.x, there is no upstream release. You either get a vendor backport, build from the backport branch, or migrate to a supported branch. Treat the vendor route as a bridge, not a plan.

How the flaws work

The advisories describe two different memory-lifecycle bugs. I am keeping this at the level the advisories publish and leaving out payload details on purpose.

CVE-2026-109618, “RCE via OOM corruption.” PHP uses longjmp() to bail out of a request when it runs out of memory. In some contexts, request memory is reachable before it is fully initialized. If an allocation fails at that point, the request is left in an invalid state, and request shutdown then reads or branches on it. The failing allocation does not need to be related to the invalid memory.

The advisory lists several ways to run a request out of memory while staying inside its apparent limits, all around multipart parsing: a multipart body without a usable declared content length that slips past post_max_size, parts with an unlimited number of headers, and empty file controls that do not count toward max_file_uploads but still build metadata arrays.

CVE-2026-109619, “RCE via stale global state.” A persistent worker keeps some global state (error, session, object, extension state) that points at memory owned by one request. If a fatal error, including an out-of-memory one, interrupts the request before that state is reset, the heap is freed while the worker still refers to it. A later operation that runs before normal request initialization can then use the stale pointer: a use-after-free. It needs a producer and a consumer, and in the demonstrated cases they are different HTTP requests handled by the same worker.

The confirmed consumers are INI diagnostics raised before request initialization and session upload progress. session.upload_progress.enabled is on by default and no session_start() call is needed. The strongest demonstrated case is PHP 8.5 with fatal_error_backtraces enabled.

Impact depends on the SAPI

  • Apache mod_php is the worst case for 109618: request shutdown runs even when startup failed, so the flaw is reachable before any application code runs. RCE was demonstrated over HTTP with default memory and input limits. The 109619 backtrace case was also confirmed against mod_php.
  • PHP-FPM exits a child when request startup fails, which blunts the simplest sequence. The advisories describe it as susceptible through application-level paths. For 109619 a session-lifecycle RCE was validated on FPM, but it needs a suitable application operation. For 109618 the advisory says no complete FPM exploit has been demonstrated, while the PHP Foundation says RCE was confirmed on FPM through application-level code paths.
  • FrankenPHP is likely susceptible to 109618 by source analysis, and LSAPI is a conditional candidate. Neither was validated.

The confirmed impact is unauthenticated code execution as the web worker account. For 109619 the advisory also lists heap use-after-free and memory disclosure. Reliability depends on the PHP build, extensions, frontend and allocator layout.

Is it being exploited?

  • One of the reporting firms published a proof-of-concept video by mistake after the leak, and copies have been circulating since. The PHP security team says it went through the PoCs that surfaced and found no functional exploit at the time of release (PHP Foundation)
  • watchTowr tells a different story: it reports exploitation attempts in the wild from October 21, along with a PoC tool called “PHP2Shell” making the rounds (watchTowr). Even if you weigh that as one vendor’s account, the safe move is to plan as if exploitation is active.
  • Public repositories claiming to hold detection rules or indicators are already out there. Treat them with caution before putting anything from them into your tooling.

Reduce exposure at the edge: WAF and defense in depth

A WAF is a compensating control, not a fix. The bug is in the PHP interpreter. A rule at the edge does not update PHP, does not help if the origin is reachable around the edge, and only matches request shapes someone has already seen. Akamai says the same in its own write-up: “the most effective defense continues to be the prompt application of vendor patches” (Akamai). Use the controls below to buy time, shrink the blast radius and notice if something got through. The patch comes in the next section. For the general case, see my post A WAF Is Not a Patch.

The map

The six layers below are the whole defense. Traffic crosses five of them top to bottom and every layer reports into the sixth. Only layer 4 removes the vulnerability. Layers 1 to 3 reduce the chance that a hostile request reaches the multipart parser, layer 5 limits what a compromised worker can do, and layer 6 is how you find out the others failed.

Each layer maps to a security-by-design principle:

LayerWhat it doesPrinciple
1. Edge (WAF)Managed rule, custom virtual patch, rate limits, origin lock-downDefense in depth, fail safe. An independent control in front of the app, and the origin lock-down stops the edge being bypassed.
2. Proxy / web serverHard caps on size, parts, headers, nesting; reject multipart without a usable lengthSecure defaults, fail safe. The PHP advisory itself says to cap these at the frontend. The limits hold even if the WAF is misconfigured.
3. ApplicationAuthenticated, CSRF-protected uploads only where needed; validated input; fail closedLeast privilege. Anonymous users never reach multipart paths they do not need. On mod_php, CVE-2026-109618 triggers before application code runs, so this layer reduces exposure but does not close it.
4. PHP runtimePatch, restart, interim ini changesPatch management. The only layer that fixes the root cause. The interim ini changes are partial.
5. Container / infrastructureRebuild, non-root, read-only filesystem, memory limit, egress filter, scoped secretsLeast privilege, blast-radius reduction. Assume the parser can be compromised: a worker that cannot spawn tools, write to disk or reach the network is worth little to an attacker.
6. Monitoring / responseEvents to a SIEM, host telemetry, a runbookObservability. Rules will have gaps, and detection time bounds the damage.

Akamai as the worked example

I use Akamai App and API Protector because it is the vendor whose guidance I read for this. Akamai released Adaptive Security Engine rule 3000991 v1 (“PHP Remote Code Execution Attack Detected (CVE-2026-109618, CVE-2026-109619)”) and says its existing command-injection rules mitigate weaponized payloads. The same logic carries over to other WAFs.

One limit on what follows. Menu names and available match conditions vary by contract and product version, so confirm each one in your own Control Center.

1. Prerequisites. Identify the security policies and hostnames that front PHP applications, because rules attach to policies and a missed hostname is an unprotected app. Identify which paths legitimately accept multipart/form-data: everything else is a candidate for “no multipart”. Confirm the origin cannot be reached around Akamai (step 6) before anything else.

2. Confirm the managed protection is on, and in Deny. Find rule 3000991 in the policy’s Adaptive Security Engine view and check that its action is Deny, not Alert. Akamai says App and API Protector customers are protected, but its post does not state the per-policy default action, so do not assume it. Turn on auto-update of Rapid Rules, or review new rules daily during the incident. Keep the command injection, web attack tool, web protocol attack and file inclusion groups in Deny: they matter for what happens after a payload lands, not for the memory-corruption trigger itself. Google Cloud recommends the equivalent categories for Cloud Armor. If you need an exception, scope it to one path and one rule, never a whole group.

3. Custom rules as a virtual patch, in Alert first. Aim to shrink the reachable multipart surface using only conditions an edge can evaluate reliably.

RulePurposeConfidence
A. Multipart outside the allow-listDeny multipart/form-data POSTs to any path that does not need uploadsStrong: header and path only
B. Chunked multipartAlert, then deny, multipart/form-data with Transfer-Encoding: chunked or no Content-LengthStrong, if none of your clients send chunked uploads. This is my inference from the advisory, not an advisory recommendation
C. Oversize multipartDeny multipart whose Content-Length is above the per-path capStrong for the declared length, silent about decoded size
D. Upload-progress fieldAlert on the PHP_SESSION_UPLOAD_PROGRESS field name in the bodyWeak: limited by body inspection, not needed by CVE-2026-109618, easily renamed
E. Oversized-body gapAlert on multipart bodies larger than the WAF’s inspection limitCloses the “the WAF never read it” blind spot (Google Cloud suggests the same kind of rule)

4. Rate controls. Add a rate policy for POSTs to multipart-capable paths, keyed by client IP. CVE-2026-109619 needs a producer request followed by a consumer request, so bursts are a usable signal. Start from your observed peak legitimate rate, not a guessed number, and start in Alert.

5. Roll out from Alert to Deny, and test. The order is the point:

  1. Baseline: log the current multipart traffic for two to seven days if you can.
  2. Deploy the custom rules in Alert.
  3. Review events daily, grouped by rule, path, client and user agent.
  4. On a false positive, scope or fix the rule. Never disable the group.
  5. When a rule has been clean for the period you chose, promote it to Deny, one rule at a time, lowest risk first.
  6. Watch the 4xx rate, the upload success rate and support tickets. On a regression, go back to Alert and keep the evidence.
  7. Keep the rules until PHP is patched everywhere, then retire them or keep them as hardening.

Expect false positives from large legitimate uploads, bulk forms with many array fields, upload-progress bars and clients that send chunked multipart. Keep a short list of known-good clients (mobile apps, integrations) and test them before each promotion to Deny.

Do not run exploit code or the public PoC to test your rules, in production or in staging. It can be malicious, and a successful test crashes or compromises workers. Use benign synthetic requests against a staging hostname in the same policy. These are examples to adapt; the hostnames and paths are placeholders:

6. Lock down the origin. Without this, everything above is optional for an attacker. Allow origin traffic only from Akamai (Site Shield, or an origin firewall allow-list of Akamai ranges plus a shared secret or mTLS where available), because an origin that accepts direct traffic bypasses the WAF completely. Verify from an outside network that the origin IP does not answer, and review DNS history and old hostnames that may still point straight at it.

7. Logging and SIEM. Send security events and delivery logs (DataStream) to your SIEM, including request ID, hostname, path, method, client IP, Content-Type, Content-Length, Transfer-Encoding, response code, matched rule IDs and actions. Useful detections to adapt:

  • Any hit on rule 3000991 or on custom rules A to E, grouped by client and path.
  • Multipart POST count per path per hour against your baseline.
  • Spikes in 5xx from PHP origins within minutes of a multipart burst, which looks like worker crashes.
  • A client that sent an alerted request and then a second request to the same host within seconds, the producer and consumer pattern of CVE-2026-109619.

Correlate with host telemetry: a shell or unexpected child process spawned by php-fpm or Apache workers is a compromise indicator, not a WAF event.

What each layer is not

  • The WAF is not a patch: PHP stays vulnerable for any request that reaches the origin.
  • Proxy limits are not a patch either. The advisory describes them as partial.
  • The ini changes are partial and disputed. watchTowr calls them ineffective, and the PHP project says none is a complete mitigation.
  • Container hardening limits the damage after a compromise. It does not prevent the memory corruption.
  • Only the PHP update closes both CVEs. For 8.1 and older, use a vendor backport or the source backport branch, or take the service off the internet.

Patch PHP

The advisories are blunt about the order of things: updating to a patched release is the only complete fix. Everything else is a stopgap.

Docker images

The official php image compiles PHP from source, so the PHP version in the image is the tag’s version. Fixed tags exist for every active variant: 8.5.12, 8.4.27, 8.3.36 and 8.2.35, each in -cli, -fpm, -apache and -zts flavors, on Debian (-trixie, -bookworm) and Alpine (-alpine3.24, -alpine3.23, plus the floating -alpine alias). There is no -apache flavor on Alpine. I checked through the Docker Hub API on October 22 that all four versions exist in 27 non-RC variants each. Examples: php:8.5.12-fpm-alpine, php:8.4.27-cli-trixie, php:8.3.36-apache-bookworm. There are no patched official images for 8.1 and older: the last 8.1 image (8.1.34) was built in December 2025.

Pin by version and by digest. A version tag (8.5.12-fpm-alpine) tells you which PHP you run, but it is mutable: Docker rebuilds the same tag when the base OS changes. In my check the 8.5.12-fpm-alpine manifest list had a different digest from the floating 8.5-fpm-alpine, so do not assume that floating and versioned tags point to the same image. A digest (@sha256:...) is immutable and reproducible, but it freezes the OS packages too, so you have to bump it deliberately (Dependabot and Renovate can do that). Do both: the version for readability, the digest for reproducibility.

The digest is the manifest list digest, so it works on amd64 and arm64. Record the digest you deploy: you need it for rollback. I do not hardcode digests here because they change whenever Docker rebuilds a tag.

Do not trust a clean image scan for these CVEs. PHP in the official images is built into /usr/local, so it is not an apk or dpkg package. In a test on October 22, Trivy 0.74.0 with a vulnerability database updated that day reported no finding for either CVE on php:8.5.11-cli-alpine, which is vulnerable. Keep scanning for everything else, and use the version check below for these two CVEs. If you want a scanner’s result as evidence, run it once against a known-vulnerable image first and see whether it flags it. I did not test Grype.

Also check the other images that contain PHP: Composer images, CI runners, dev containers, php:*-cli stages used in builds, and base images from your platform team.

If you really cannot patch yet

These come from the advisories. They are partial, they need a restart of every worker, and they belong in system or per-directory configuration, not in ini_set() or .user.ini, which run too late.

  • session.upload_progress.enabled=0 removes the demonstrated early session path for CVE-2026-109619. The advisory suggests keeping it off even after patching if you do not use the feature.
  • On PHP 8.5, fatal_error_backtraces=0 removes the producer used in the confirmed CVE-2026-109619 RCE. It covers only that path.
  • memory_limit=-1, locked with php_admin_value, is the advisory’s primary configuration mitigation for CVE-2026-109618, because it removes the predictable limit the exploit depends on. It is not complete, and it costs you resource protection: if mmap() or another allocation still fails, the vulnerable path is reachable. Use container or cgroup limits instead, and never RLIMIT_AS or RLIMIT_DATA, which make the vulnerable path easier to hit. A cgroup kill can also take down the master and all workers.
  • A low post_max_size (the php.net advisory suggests 8M without uploads and 32M with uploads), with upload_max_filesize below it, shrinks the out-of-memory surface. It does not cover multipart requests without a usable Content-Length, so enforce the same limits at the proxy.
  • pm.max_requests=1 breaks the same-worker requirement of CVE-2026-109619, at a real performance cost. The advisory says to use it “if performance is not a factor”.

For CVE-2026-109619 the advisory states that there is no complete generic configuration mitigation. Hiding errors with error_reporting, display_errors or @ does not help.

Verify what is actually running

Installing a package or building an image does not prove that the running process changed. Check the running thing.

Host or VM.

A CI gate that fails on vulnerable versions

PHP_VERSION is compared with the first fixed release of the same branch. For 8.1 and older, the check fails unless you explicitly confirm a vendor backport. Save it as check-php-patched.php:

<?php
// Fails (exit 1) when the running PHP is older than the first release that
// fixes CVE-2026-109618 / CVE-2026-109619 for its branch.
const FIXED = ['8.2' => '8.2.35', '8.3' => '8.3.36', '8.4' => '8.4.27', '8.5' => '8.5.12'];

$branch = PHP_MAJOR_VERSION . '.' . PHP_MINOR_VERSION;

if (isset(FIXED[$branch])) {
    $ok = version_compare(PHP_VERSION, FIXED[$branch], '>=');
    $need = FIXED[$branch];
} elseif (version_compare($branch, '8.5', '>')) {
    $ok = true; // newer than every branch listed in the advisories
    $need = 'n/a';
} else {
    // 8.1 and older: no upstream release. Only a vendor backport can make this safe,
    // and PHP_VERSION cannot prove one. Opt in explicitly after checking the vendor.
    $ok = getenv('ALLOW_VENDOR_BACKPORT') === '1';
    $need = 'vendor backport';
}

printf("PHP %s (branch %s, need >= %s): %s\n", PHP_VERSION, $branch, $need, $ok ? 'OK' : 'VULNERABLE');
exit($ok ? 0 : 1);

I ran it against the official images on October 22. php:8.5.11-cli-alpine and php:8.4.26-cli-alpine printed VULNERABLE and exited 1. php:8.5.12-cli-alpine and php:8.4.27-cli-alpine printed OK and exited 0. php:8.1-cli-alpine (8.1.34) printed VULNERABLE, and OK with ALLOW_VENDOR_BACKPORT=1.

Its limit: on a distro package whose PHP_VERSION is old but patched (Ubuntu 24.04 8.3.6...), it reports VULNERABLE. On distro hosts, check the package version against the vendor tracker, and set ALLOW_VENDOR_BACKPORT=1 only after you have done that. It also cannot see a patch applied from a source backport.

Run it in three places. In the Dockerfile, so that a build cannot succeed on an unpatched base. In CI against the built image, which also catches images built from a different Dockerfile: build the image as above, then run docker run --rm -i app:ci php < check-php-patched.php. And on a schedule across the containers on a host:

Rollout and rollback

  1. Inventory every place PHP runs: web hosts, workers, cron, CLI jobs, build images, dev containers. Record branch, version, SAPI and internet exposure.
  2. Triage by exposure. Internet-facing mod_php first, then FPM behind a public proxy, then internal services and CLI. Do not wait for a full regression cycle on the first group: watchTowr reports exploitation, and a public exploit tool leaked before the release.
  3. Staging. Deploy the fixed version, run your tests, upload a large file and a multi-field form, and check an endpoint that normally uses a lot of memory.
  4. Canary. Send 5 to 10 percent of traffic to the new version for at least one traffic cycle.
  5. Full rollout as a rolling restart in batches, confirming each batch with the checks above.
  6. Decommission interim mitigations you no longer need, and delete old images from registries so no one pulls an old tag by mistake.

During the canary and for a week after, watch the 5xx rate and p95 latency, worker restarts (FPM child exited), PHP errors such as Allowed memory size ... exhausted and segmentation faults (exited on signal 11), per-worker memory and container OOM kills, upload failures and 413/400 responses if you tightened limits, and the security signals listed in the WAF section.

Rolling back to a vulnerable version reopens an exploitable hole, so prefer rolling forward. If you must roll back, redeploy the previous image by the digest you recorded rather than by tag, and put the interim mitigations and a WAF rule in place first. Set a deadline for the second attempt: a rollback is a bug report against your tests, not a decision to stay unpatched.

If you suspect exploitation (shells under the web user, unexplained crashes before the patch), patching is not enough. Rotate the secrets the web user could read, review file changes, and rebuild from a clean image rather than cleaning a running one.

What I would do today

  1. Find every PHP you run. php -v on servers, but also base images in your Dockerfiles, CI images, and anything a hosting provider manages for you. Containers are the usual blind spot.
  2. Upgrade to a patched release (8.2.35, 8.3.36, 8.4.27 or 8.5.12 or later) and redeploy. Updating a package on a host does nothing for an image that has already been built.
  3. Rebuild images without cache. Pinned or cached base layers keep serving the vulnerable version until you pull the new tag and rebuild.
  4. Restart long-lived workers. The advisory says to restart every worker. An updated binary on disk is irrelevant until PHP-FPM, Apache and friends are restarted.
  5. Verify the running version, not the image you intended to deploy.
  6. While you roll out: confirm Akamai rule 3000991 (or your WAF’s equivalent) and the command-injection rules are in Deny, lock the origin to the edge, and run the multipart rules in Alert first.
  7. Plan the end-of-life migration. If you are on 8.1 or older, this is no longer a someday task. In the meantime, ask your vendor about a backport.
  8. Check managed platforms. On Google Cloud, App Engine standard patches supported runtimes automatically, but App Engine flexible does not, and Cloud Run only updates automatically when automatic base image updates are enabled (Google Cloud). Other providers have their own rules; do not assume.
  9. Read the primary sources before acting on anyone’s summary, including this one.
