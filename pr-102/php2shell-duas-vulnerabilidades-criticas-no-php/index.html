Duas vulnerabilidades críticas no próprio runtime do PHP foram divulgadas em 21 de outubro de 2026: CVE-2026-109618 e CVE-2026-109619, apelidadas de “PHP2Shell”. Ambas têm CVSS 9.2 (v4.0) e podem expor aplicações a execução remota de código sem autenticação e a divulgação de memória.

Não se trata de um bug em um framework ou plugin. Está no núcleo do PHP, então tanto faz se você usa WordPress, Laravel, Symfony, Zend ou um script de dez anos atrás.

O que é afetado

Segundo o Google Cloud, “todas as versões do PHP da 5.4 até a 8.5.11” são vulneráveis. As correções estão no PHP 8.5.12, 8.4.27, 8.3.36 e 8.2.35. O projeto PHP não vai lançar correções para a 8.1 ou anteriores, que já atingiram o fim de vida.

Esse último ponto é o incômodo: se você está na 8.1, 7.x ou 5.x, não há patch para aplicar. A única correção é migrar para uma branch suportada.

Como as falhas funcionam (resumidamente)

O Google Cloud descreve cada uma em uma frase:

  • CVE-2026-109618: o tratamento de falta de memória pode interromper o PHP enquanto os dados internos da requisição estão apenas parcialmente inicializados, e a limpeza da requisição pode então tratar os dados inválidos como válidos.
  • CVE-2026-109619: o estado interno pertencente à requisição pode sobreviver depois que a memória que o sustentava foi liberada, de modo que uma requisição posterior tratada pelo mesmo worker pode usar esse estado obsoleto antes de a inicialização normal reiniciá-lo.

Ambos são bugs de ciclo de vida de memória no tratamento de requisições. O segundo lembra que workers de longa duração (o PHP-FPM, por exemplo) carregam estado de uma requisição para a seguinte, e um use-after-free ali pode atravessar fronteiras entre requisições. O Google também observa que circunstâncias atenuantes podem dificultar a exploração; nenhuma das fontes descreve o caminho do exploit em detalhes.

O que eu faria hoje

  1. Encontre todo PHP que você roda. php -v nos servidores, mas também imagens base nos Dockerfiles, imagens de CI e o que a hospedagem gerencia por você. Contêineres são o ponto cego de sempre.
  2. Atualize para uma versão corrigida (8.2.35, 8.3.36, 8.4.27 ou 8.5.12 ou superior) e faça o redeploy. Atualizar um pacote no host não faz nada por uma imagem que já foi construída.
  3. Reconstrua as imagens. Camadas base fixadas ou em cache continuam servindo a versão vulnerável até você reconstruir sem cache.
  4. Planeje a migração de fim de vida. Se você está na 8.1 ou anterior, isso deixou de ser tarefa para “algum dia”.
  5. Reinicie workers de longa duração. Um binário atualizado em disco é irrelevante até o PHP-FPM e similares serem reiniciados.
  6. Verifique plataformas gerenciadas. No Google Cloud, o App Engine standard corrige runtimes suportados automaticamente, mas o App Engine flexible não, e o Cloud Run só atualiza sozinho quando as atualizações automáticas da imagem base estão ativadas. Outros provedores terão regras próprias; não presuma.
  7. Leia as fontes primárias: o advisory do PHP e os advisories do GitHub para estes CVEs, antes de agir com base no resumo de qualquer pessoa, inclusive este.
