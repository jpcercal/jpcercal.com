Duas vulnerabilidades críticas no próprio runtime do PHP foram divulgadas em 21 de outubro de 2026: CVE-2026-109618 e CVE-2026-109619, apelidadas de “PHP2Shell”. Ambas têm CVSS 9.2 (v4.0) e podem levar a execução remota de código sem autenticação. A divulgação foi antecipada de 22 de outubro depois que os IDs dos CVEs vazaram em 20 de outubro (PHP Foundation).

Não se trata de um bug em um framework ou plugin. Está no núcleo do PHP, então tanto faz se você usa WordPress, Laravel, Symfony, Zend ou um script de dez anos atrás.

Atualizei este post depois de ler os dois advisories de segurança do GitHub, o texto da PHP Foundation e as páginas dos fornecedores listadas nas referências. Quando uma afirmação depende de um único fornecedor ou de uma página que não consegui ler por inteiro, eu aviso.

A versão curta: atualize o PHP para 8.5.12, 8.4.27, 8.3.36 ou 8.2.35, reinicie todos os workers e confira a versão que está de fato em execução. Um WAF pode ganhar tempo, mas não é uma correção. A seguir: como as falhas funcionam, o que um WAF e a defesa em profundidade podem e não podem fazer (com um mapa de mitigação e um exemplo com Akamai), como aplicar o patch no PHP e nas imagens Docker, como verificar e as fontes.

O que é afetado

As versões corrigidas são PHP 8.5.12, 8.4.27, 8.3.36 e 8.2.35. Os dois CVEs são corrigidos pelas mesmas versões. Qualquer versão anterior a essas na mesma branch é afetada.

Para as branches mais antigas, as fontes divergem, e esta é a parte incômoda:

  • Os advisories do GitHub (GHSA-w8hw-w9fx-j79w e GHSA-6wmf-4rv5-p3rp) listam as branches 8.2 a 8.5.
  • O Google Cloud diz que “todas as versões do PHP da 5.4 até a 8.5.11” são vulneráveis (Google Cloud).
  • O PHP upstream não publica release para a 8.1 ou anteriores. A equipe de segurança publicou backports mínimos do código-fonte para a 7.4, 8.0 e 8.1 como branches no php-src, para quem compila a partir do código-fonte e não tem um fornecedor com suporte de longo prazo (links na seção de correção).
  • Alguns fornecedores entregam pacotes com backport para branches antigas: a Ubuntu lista pacotes corrigidos do 14.04 ao 26.10 (os mais antigos via Ubuntu Pro) e a Zend lista builds do ZendPHP para 7.2, 7.3, 7.4 e 8.1. A página da Zend diz que a falha afeta todas as versões 5, 7 e 8.0/8.1 do PHP (Ubuntu, Zend).

Então, se você está na 8.1, 7.x ou 5.x, não existe release upstream. Você consegue um backport do fornecedor, compila a partir da branch de backport ou migra para uma branch suportada. Trate a rota do fornecedor como uma ponte, não como um plano.

Como as falhas funcionam

Os advisories descrevem dois bugs diferentes de ciclo de vida de memória. Mantenho este resumo no nível que os advisories publicam e deixo de fora, de propósito, os detalhes de payload.

CVE-2026-109618, “RCE via corrupção por OOM”. O PHP usa longjmp() para abandonar uma requisição quando fica sem memória. Em alguns contextos, a memória da requisição fica acessível antes de ser totalmente inicializada. Se uma alocação falha nesse momento, a requisição fica em um estado inválido, e o encerramento da requisição então lê ou toma decisões com base nele. A alocação que falha não precisa ter relação com a memória inválida.

O advisory lista várias formas de estourar a memória de uma requisição mantendo-se dentro dos limites aparentes, todas em torno do parsing de multipart: um corpo multipart sem um tamanho declarado utilizável que escapa do post_max_size, partes com um número ilimitado de headers e controles de arquivo vazios que não contam para o max_file_uploads, mas ainda assim constroem arrays de metadados.

CVE-2026-109619, “RCE via estado global obsoleto”. Um worker persistente mantém algum estado global (de erro, sessão, objeto, extensão) que aponta para memória pertencente a uma requisição. Se um erro fatal, inclusive um de falta de memória, interrompe a requisição antes de esse estado ser reiniciado, o heap é liberado enquanto o worker ainda o referencia. Uma operação posterior, executada antes da inicialização normal da requisição, pode então usar o ponteiro obsoleto: um use-after-free. É preciso um produtor e um consumidor, e nos casos demonstrados eles são requisições HTTP diferentes tratadas pelo mesmo worker.

Os consumidores confirmados são os diagnósticos de INI emitidos antes da inicialização da requisição e o progresso de upload de sessão. O session.upload_progress.enabled vem ativado por padrão e não é preciso chamar session_start(). O caso demonstrado mais forte é o PHP 8.5 com fatal_error_backtraces ativado.

O impacto depende da SAPI

  • Apache mod_php é o pior caso para o 109618: o encerramento da requisição roda mesmo quando a inicialização falhou, então a falha é alcançável antes de qualquer código da aplicação executar. O RCE foi demonstrado via HTTP com os limites padrão de memória e de entrada. O caso do backtrace do 109619 também foi confirmado no mod_php.
  • PHP-FPM encerra um processo filho quando a inicialização da requisição falha, o que atenua a sequência mais simples. Os advisories o descrevem como suscetível por caminhos no nível da aplicação. Para o 109619, um RCE no ciclo de vida da sessão foi validado no FPM, mas exige uma operação adequada da aplicação. Para o 109618, o advisory diz que nenhum exploit completo para FPM foi demonstrado, enquanto a PHP Foundation diz que o RCE foi confirmado no FPM por caminhos de código no nível da aplicação.
  • FrankenPHP provavelmente é suscetível ao 109618 por análise do código-fonte, e LSAPI é um candidato condicional. Nenhum dos dois foi validado.

O impacto confirmado é execução de código sem autenticação com a conta do worker web. Para o 109619, o advisory também lista use-after-free de heap e divulgação de memória. A confiabilidade depende do build do PHP, das extensões, do frontend e do layout do alocador.

Está sendo explorado?

  • Um vídeo de prova de conceito de uma das empresas que reportaram as falhas foi publicado por engano depois do vazamento, e cópias circularam. A equipe de segurança do PHP diz que inspecionou as PoCs que apareceram e não encontrou um exploit funcional na hora do release (PHP Foundation).
  • A watchTowr diz que viu tentativas de exploração na internet a partir de 21 de outubro e que uma ferramenta de PoC chamada “PHP2Shell” estava circulando (watchTowr). É a afirmação de um único fornecedor e não consegui confirmá-la de forma independente. Planeje como se a exploração estivesse ativa.
  • Existem repositórios públicos que dizem conter regras de detecção ou indicadores. Não os auditei e não vou linká-los.

Onde as fontes divergem

  • Branches antigas. O Google diz 5.4 em diante, os advisories listam 8.2 a 8.5 e os fornecedores entregam backports. Já tratado acima.
  • Explorabilidade no FPM. O advisory do 109618 diz que não há exploit completo para FPM, a PHP Foundation diz que o RCE foi confirmado no FPM por caminhos de código da aplicação, e a Red Hat considera difícil na prática porque os workers do FPM encerram em falhas de inicialização precoces (Red Hat). Minha leitura: o FPM está exposto, mas de forma condicionada à aplicação.
  • Severidade. A PHP Foundation confirma 9.2 (CVSS v4.0) como a pontuação real; o 10.0 que circulou em 20 de outubro estava errado. A página da Red Hat para o CVE-2026-109618 mostra uma pontuação própria CVSS v3.1 de 8.1 (“Important”, por causa da complexidade do ataque) ao lado de uma pontuação NVD de 9.8. Li isso na página da Red Hat, não no registro do NVD em si.
  • Mitigações por configuração. Os advisories oferecem ajustes parciais e dizem com todas as letras que só o patch é completo. A watchTowr chama as mitigações baseadas em INI de ineficazes. Trato-as, na melhor das hipóteses, como um paliativo.
  • Crédito da descoberta. As fontes citam empresas diferentes. Deixo o crédito de fora em vez de chutar.

Reduza a exposição na borda: WAF e defesa em profundidade

Um WAF é um controle compensatório, não uma correção. O bug está no interpretador do PHP. Uma regra na borda não atualiza o PHP, não ajuda se a origem puder ser alcançada contornando a borda e só reconhece formatos de requisição que alguém já viu. A própria Akamai diz o mesmo: “a defesa mais eficaz continua sendo a aplicação rápida dos patches do fornecedor” (Akamai). Use os controles abaixo para ganhar tempo, reduzir o raio de impacto e perceber se algo passou. O patch vem na próxima seção.

O que a borda consegue e não consegue ver

  • O formato de uma requisição (content type, tamanho declarado, chunking, caminho, tamanho) é visível nos headers. O interior do corpo (número de partes, aninhamento) só é visível até o limite de inspeção de corpo do WAF. Prefira condições de header e de caminho: elas não sofrem esse limite.
  • Os advisories descrevem estratégias de falta de memória baseadas no formato e no tamanho do corpo multipart, e não em um nome de campo específico. Uma regra só sobre PHP_SESSION_UPLOAD_PROGRESS é um sinal fraco e também casa com barras de progresso de upload legítimas.
  • O CVE-2026-109619 precisa de uma requisição produtora e uma consumidora no mesmo worker. O bloqueio por requisição só funciona se a produtora for pega. Anomalias de taxa e de sequência ajudam aqui.
  • Assinaturas baseadas no user agent ou na string de boundary de uma PoC pública são triviais de evadir, então eu não confiaria nelas.

O mapa

As seis camadas abaixo formam a defesa inteira. O tráfego atravessa cinco delas, de cima para baixo, e todas reportam para a sexta. Só a camada 4 remove a vulnerabilidade. As camadas 1 a 3 reduzem a chance de uma requisição hostil chegar ao parser de multipart, a camada 5 limita o que um worker comprometido consegue fazer e a camada 6 é como você descobre que as outras falharam.

Cada camada corresponde a um princípio de segurança desde a concepção (security by design):

CamadaO que fazPrincípio
1. Borda (WAF)Regra gerenciada, patch virtual próprio, limites de taxa, trava de acesso à origemDefesa em profundidade, falhar de forma segura. Um controle independente na frente da aplicação, e a trava na origem impede que a borda seja contornada.
2. Proxy / servidor webLimites rígidos de tamanho, partes, headers e aninhamento; rejeitar multipart sem tamanho utilizávelPadrões seguros, falhar de forma segura. O próprio advisory do PHP manda limitar isso no frontend. Os limites valem mesmo que o WAF esteja mal configurado.
3. AplicaçãoUploads autenticados e protegidos contra CSRF só onde necessário; entrada validada; falhar fechadoPrivilégio mínimo. Usuários anônimos não chegam a caminhos multipart de que não precisam. No mod_php, o CVE-2026-109618 dispara antes de o código da aplicação rodar, então esta camada reduz a exposição, mas não a elimina.
4. Runtime do PHPPatch, reinício, ajustes provisórios de iniGestão de patches. A única camada que corrige a causa raiz. Os ajustes provisórios de ini são parciais.
5. Contêiner / infraestruturaRebuild, non-root, sistema de arquivos somente leitura, limite de memória, filtro de egress, segredos restritosPrivilégio mínimo, redução do raio de impacto. Parta do princípio de que o parser pode ser comprometido: um worker que não consegue iniciar ferramentas, gravar em disco nem acessar a rede vale pouco para um atacante.
6. Monitoramento / respostaEventos para um SIEM, telemetria de host, um runbookObservabilidade. As regras terão lacunas, e o tempo de detecção limita o dano.

Akamai como exemplo prático

Uso o Akamai App and API Protector porque é o fornecedor cujas orientações li para este post. A Akamai lançou a regra 3000991 v1 do Adaptive Security Engine (“PHP Remote Code Execution Attack Detected (CVE-2026-109618, CVE-2026-109619)”) e diz que suas regras existentes de command injection mitigam payloads armados. A mesma lógica vale para outros WAFs.

Duas ressalvas sobre o que segue. Os nomes de menus e as condições de correspondência disponíveis variam conforme o contrato e a versão do produto, então confirme cada um no seu próprio Control Center. E não testei nada disso em um tenant Akamai real.

1. Pré-requisitos. Identifique as políticas de segurança e os hostnames que ficam na frente de aplicações PHP, porque as regras se associam a políticas e um hostname esquecido é uma aplicação desprotegida. Identifique quais caminhos aceitam multipart/form-data de forma legítima: todo o resto é candidato a “sem multipart”. Confirme que a origem não pode ser alcançada contornando a Akamai (passo 6) antes de qualquer outra coisa.

2. Confirme que a proteção gerenciada está ligada, e em Deny. Encontre a regra 3000991 na visão do Adaptive Security Engine da política e confira que a ação é Deny, e não Alert. A Akamai diz que clientes do App and API Protector estão protegidos, mas o post dela não informa a ação padrão por política, então não presuma. Ative a atualização automática das Rapid Rules ou revise as regras novas diariamente durante o incidente. Mantenha em Deny os grupos de command injection, web attack tool, web protocol attack e file inclusion: eles importam para o que acontece depois que um payload chega, não para o gatilho de corrupção de memória em si. O Google Cloud recomenda as categorias equivalentes para o Cloud Armor. Se precisar de uma exceção, restrinja-a a um caminho e a uma regra, nunca a um grupo inteiro.

3. Regras customizadas como patch virtual, primeiro em Alert. O objetivo é reduzir a superfície de ataque multipart alcançável usando apenas condições que uma borda consegue avaliar com confiabilidade.

RegraFinalidadeConfiança
A. Multipart fora da lista de permitidosNegar POSTs multipart/form-data para qualquer caminho que não precise de uploadForte: só header e caminho
B. Multipart com chunkingAlertar e depois negar multipart/form-data com Transfer-Encoding: chunked ou sem Content-LengthForte, se nenhum dos seus clientes envia uploads com chunking. É uma inferência minha a partir do advisory, não uma recomendação dele
C. Multipart grande demaisNegar multipart cujo Content-Length esteja acima do limite do caminhoForte para o tamanho declarado, silenciosa sobre o tamanho decodificado
D. Campo de progresso de uploadAlertar sobre o nome de campo PHP_SESSION_UPLOAD_PROGRESS no corpoFraca: limitada pela inspeção de corpo, desnecessária para o CVE-2026-109618, fácil de renomear
E. Lacuna de corpo grande demaisAlertar sobre corpos multipart maiores que o limite de inspeção do WAFFecha o ponto cego do “o WAF nunca leu isso” (o Google Cloud sugere o mesmo tipo de regra)

4. Controles de taxa. Adicione uma política de taxa para POSTs em caminhos que aceitam multipart, por IP de cliente. O CVE-2026-109619 precisa de uma requisição produtora seguida de uma consumidora, então rajadas são um sinal utilizável. Parta do pico legítimo que você observou, não de um número chutado, e comece em Alert.

5. Evolua de Alert para Deny e teste. A ordem é o ponto:

  1. Linha de base: registre o tráfego multipart atual por dois a sete dias, se puder.
  2. Implante as regras customizadas em Alert.
  3. Revise os eventos todo dia, agrupados por regra, caminho, cliente e user agent.
  4. Diante de um falso positivo, restrinja ou corrija a regra. Nunca desative o grupo.
  5. Quando uma regra estiver limpa pelo período que você escolheu, promova-a para Deny, uma regra por vez, começando pela de menor risco.
  6. Acompanhe a taxa de 4xx, a taxa de sucesso de uploads e os chamados de suporte. Em caso de regressão, volte para Alert e guarde as evidências.
  7. Mantenha as regras até o PHP estar corrigido em todo lugar; depois aposente-as ou mantenha-as como hardening.

Espere falsos positivos de uploads legítimos grandes, formulários extensos com muitos campos de array, barras de progresso de upload e clientes que enviam multipart com chunking. Mantenha uma lista curta de clientes conhecidos e confiáveis (apps móveis, integrações) e teste-os antes de cada promoção para Deny.

Não rode código de exploit nem a PoC pública para testar suas regras, nem em produção nem em staging. Ela pode ser maliciosa, e um teste bem-sucedido derruba ou compromete workers. 6. Trave o acesso à origem. Sem isso, tudo o que está acima é opcional para um atacante. Permita tráfego na origem apenas vindo da Akamai (Site Shield, ou uma lista de permissão no firewall da origem com os ranges da Akamai mais um segredo compartilhado ou mTLS, quando disponível), porque uma origem que aceita tráfego direto contorna o WAF por completo. Verifique, a partir de uma rede externa, que o IP da origem não responde, e revise o histórico de DNS e hostnames antigos que ainda possam apontar direto para ela.

7. Logs e SIEM. Envie eventos de segurança e logs de entrega (DataStream) para o seu SIEM, incluindo ID da requisição, hostname, caminho, método, IP do cliente, Content-Type, Content-Length, Transfer-Encoding, código de resposta, IDs das regras que casaram e as ações. Detecções úteis para adaptar:

  • Qualquer hit na regra 3000991 ou nas regras customizadas A a E, agrupado por cliente e caminho.
  • Contagem de POSTs multipart por caminho por hora em relação à sua linha de base.
  • Picos de 5xx em origens PHP minutos depois de uma rajada multipart, o que parece crash de workers.
  • Um cliente que enviou uma requisição alertada e, em segundos, uma segunda requisição ao mesmo host: o padrão produtor e consumidor do CVE-2026-109619.

Correlacione com a telemetria do host: um shell ou um processo filho inesperado iniciado por workers do php-fpm ou do Apache é indicador de comprometimento, não um evento de WAF.

O que cada camada não é

  • O WAF não é um patch: o PHP continua vulnerável para qualquer requisição que chegue à origem.
  • Os limites do proxy também não são um patch. O advisory os descreve como parciais.
  • Os ajustes de ini são parciais e contestados. A watchTowr os chama de ineficazes, e o projeto PHP diz que nenhum deles é uma mitigação completa.
  • O hardening de contêiner limita o dano depois de um comprometimento. Não impede a corrupção de memória.
  • Só a atualização do PHP fecha os dois CVEs. Para a 8.1 e anteriores, use um backport do fornecedor ou a branch de backport do código-fonte, ou tire o serviço da internet.

Aplique o patch no PHP

Os advisories são diretos quanto à ordem das coisas: atualizar para uma versão corrigida é a única correção completa. Todo o resto é paliativo.

A correção muda a forma como o PHP trata condições de falta de memória, então observe os endpoints que consomem muita memória depois do rollout.

Escolha o caminho de atualização

Escolha conforme o modo como o PHP chegou à máquina. Termine sempre com a verificação abaixo e com o reinício de todos os processos PHP.

Imagens Docker

A imagem oficial php compila o PHP a partir do código-fonte, então a versão do PHP na imagem é a versão da tag. Existem tags corrigidas para todas as variantes ativas: 8.5.12, 8.4.27, 8.3.36 e 8.2.35, cada uma nos sabores -cli, -fpm, -apache e -zts, em Debian (-trixie, -bookworm) e Alpine (-alpine3.24, -alpine3.23, mais o alias flutuante -alpine). Não há sabor -apache no Alpine. Conferi pela API do Docker Hub em 22 de outubro que as quatro versões existem em 27 variantes não-RC cada. Exemplos: php:8.5.12-fpm-alpine, php:8.4.27-cli-trixie, php:8.3.36-apache-bookworm. Não há imagens oficiais corrigidas para a 8.1 e anteriores: a última imagem da 8.1 (8.1.34) foi construída em dezembro de 2025.

Fixe por versão e por digest. Uma tag de versão (8.5.12-fpm-alpine) diz qual PHP você roda, mas é mutável: o Docker reconstrói a mesma tag quando o SO base muda. Na minha verificação, a manifest list de 8.5.12-fpm-alpine tinha um digest diferente do 8.5-fpm-alpine flutuante, então não presuma que tags flutuantes e versionadas apontam para a mesma imagem. Um digest (@sha256:...) é imutável e reproduzível, mas congela também os pacotes do SO, então você precisa atualizá-lo de propósito (o Dependabot e o Renovate fazem isso). Faça os dois: a versão para legibilidade, o digest para reprodutibilidade.

1

docker buildx imagetools inspect php:8.5.12-fpm-alpine --format '{{.Manifest.Digest}}'

1

FROM php:8.5.12-fpm-alpine@sha256:<digest do comando acima>

O digest é o da manifest list, então funciona em amd64 e arm64. Registre o digest que você implanta: você precisa dele para o rollback. Não deixo digests fixos aqui porque eles mudam sempre que o Docker reconstrói uma tag.

Não confie em um scan de imagem limpo para estes CVEs. O PHP das imagens oficiais é compilado em /usr/local, então não é um pacote apk nem dpkg. Em um teste em 22 de outubro, o Trivy 0.74.0, com um banco de vulnerabilidades atualizado no mesmo dia, não reportou nenhum achado para nenhum dos dois CVEs em php:8.5.11-cli-alpine, que é vulnerável. Continue escaneando tudo o mais e use a verificação de versão abaixo para estes dois CVEs. Se quiser o resultado de um scanner como evidência, rode-o antes contra uma imagem sabidamente vulnerável e veja se ele a sinaliza. Não testei o Grype.

Confira também as outras imagens que contêm PHP: imagens do Composer, runners de CI, dev containers, estágios php:*-cli usados em builds e imagens base do seu time de plataforma.

Se você realmente não consegue aplicar o patch ainda

Estas vêm dos advisories. São parciais, exigem o reinício de todos os workers e pertencem à configuração do sistema ou do diretório, não a ini_set() ou .user.ini, que rodam tarde demais.

  • session.upload_progress.enabled=0 remove o caminho precoce de sessão demonstrado para o CVE-2026-109619. O advisory sugere deixá-lo desligado mesmo depois do patch, se você não usa o recurso.
  • No PHP 8.5, fatal_error_backtraces=0 remove o produtor usado no RCE confirmado do CVE-2026-109619. Cobre só esse caminho.
  • memory_limit=-1, travado com php_admin_value, é a principal mitigação por configuração do advisory para o CVE-2026-109618, porque remove o limite previsível de que o exploit depende. Não é completa e custa a proteção de recursos: se o mmap() ou outra alocação ainda falhar, o caminho vulnerável continua alcançável. Use limites de contêiner ou cgroup no lugar, e nunca RLIMIT_AS ou RLIMIT_DATA, que facilitam atingir o caminho vulnerável. Uma morte por cgroup também pode derrubar o master e todos os workers.
  • Um post_max_size baixo (o advisory do php.net sugere 8M sem uploads e 32M com uploads), com upload_max_filesize abaixo dele, reduz a superfície de falta de memória. Não cobre requisições multipart sem um Content-Length utilizável, então imponha os mesmos limites no proxy.
  • pm.max_requests=1 quebra o requisito de mesmo worker do CVE-2026-109619, com um custo real de desempenho. O advisory manda usá-lo “se o desempenho não for um fator”.

Para o CVE-2026-109619, o advisory afirma que não existe mitigação genérica completa por configuração. Esconder erros com error_reporting, display_errors ou @ não ajuda.

<?php
// Falha (exit 1) quando o PHP em execução é mais antigo que a primeira versão que
// corrige o CVE-2026-109618 / CVE-2026-109619 para a sua branch.
const FIXED = ['8.2' => '8.2.35', '8.3' => '8.3.36', '8.4' => '8.4.27', '8.5' => '8.5.12'];

$branch = PHP_MAJOR_VERSION . '.' . PHP_MINOR_VERSION;

if (isset(FIXED[$branch])) {
    $ok = version_compare(PHP_VERSION, FIXED[$branch], '>=');
    $need = FIXED[$branch];
} elseif (version_compare($branch, '8.5', '>')) {
    $ok = true; // mais nova que todas as branches listadas nos advisories
    $need = 'n/a';
} else {
    // 8.1 e anteriores: sem release upstream. Só um backport do fornecedor pode tornar isso seguro,
    // e a PHP_VERSION não consegue provar um. Habilite explicitamente depois de checar o fornecedor.
    $ok = getenv('ALLOW_VENDOR_BACKPORT') === '1';
    $need = 'vendor backport';
}

printf("PHP %s (branch %s, need >= %s): %s\n", PHP_VERSION, $branch, $need, $ok ? 'OK' : 'VULNERABLE');
exit($ok ? 0 : 1);

Rodei o script contra as imagens oficiais em 22 de outubro. php:8.5.11-cli-alpine e php:8.4.26-cli-alpine imprimiram VULNERABLE e saíram com 1. php:8.5.12-cli-alpine e php:8.4.27-cli-alpine imprimiram OK e saíram com 0. php:8.1-cli-alpine (8.1.34) imprimiu VULNERABLE, e OK com ALLOW_VENDOR_BACKPORT=1.

O limite dele: em um pacote de distro cuja PHP_VERSION é antiga mas está corrigida (Ubuntu 24.04 8.3.6...), ele reporta VULNERABLE. Em hosts com distro, confira a versão do pacote no tracker do fornecedor e defina ALLOW_VENDOR_BACKPORT=1 só depois disso. Ele também não enxerga um patch aplicado a partir de um backport do código-fonte.

Rode-o em três lugares. No Dockerfile, para que um build não consiga ter sucesso sobre uma base sem patch. No CI, contra a imagem construída, o que também pega imagens construídas a partir de outro Dockerfile: construa a imagem como acima e rode docker run --rm -i app:ci php < check-php-patched.php. E de forma agendada nos contêineres de um host:

Rollout e rollback

  1. Faça o inventário de todo lugar onde o PHP roda: hosts web, workers, cron, jobs de CLI, imagens de build, dev containers. Registre branch, versão, SAPI e exposição à internet.
  2. Priorize por exposição. Primeiro mod_php voltado para a internet, depois FPM atrás de um proxy público, depois serviços internos e CLI. Não espere um ciclo completo de regressão no primeiro grupo: a watchTowr reporta exploração, e uma ferramenta de exploit pública vazou antes do release.
  3. Staging. Implante a versão corrigida, rode seus testes, envie um arquivo grande e um formulário com muitos campos e confira um endpoint que normalmente usa bastante memória.
  4. Canary. Mande de 5 a 10 por cento do tráfego para a versão nova por pelo menos um ciclo de tráfego.
  5. Rollout completo como reinício gradual em lotes, confirmando cada lote com as verificações acima.
  6. Desative as mitigações provisórias de que não precisa mais e apague imagens antigas dos registries, para que ninguém puxe uma tag antiga por engano.

Durante o canary e por uma semana depois, acompanhe a taxa de 5xx e a latência p95, reinícios de workers (child exited do FPM), erros do PHP como Allowed memory size ... exhausted e falhas de segmentação (exited on signal 11), memória por worker e mortes de contêiner por OOM, falhas de upload e respostas 413/400 se você apertou limites, e os sinais de segurança listados na seção do WAF.

Voltar para uma versão vulnerável reabre uma brecha explorável, então prefira avançar. Se precisar fazer rollback, reimplante a imagem anterior pelo digest que você registrou, e não pela tag, e coloque antes as mitigações provisórias e uma regra de WAF. Defina um prazo para a segunda tentativa: um rollback é um relatório de bug contra os seus testes, não uma decisão de ficar sem patch.

Se você suspeita de exploração (shells sob o usuário web, crashes inexplicados antes do patch), aplicar o patch não basta. Rotacione os segredos que o usuário web podia ler, revise as alterações em arquivos e reconstrua a partir de uma imagem limpa em vez de limpar a que está rodando.

O que eu faria hoje

  1. Encontre todo PHP que você roda. php -v nos servidores, mas também imagens base nos Dockerfiles, imagens de CI e o que a hospedagem gerencia por você. Contêineres são o ponto cego de sempre.
  2. Atualize para uma versão corrigida (8.2.35, 8.3.36, 8.4.27 ou 8.5.12 ou superior) e faça o redeploy. Atualizar um pacote no host não faz nada por uma imagem que já foi construída.
  3. Reconstrua as imagens sem cache. Camadas base fixadas ou em cache continuam servindo a versão vulnerável até você puxar a tag nova e reconstruir.
  4. Reinicie workers de longa duração. O advisory manda reiniciar todos os workers. Um binário atualizado em disco é irrelevante até o PHP-FPM, o Apache e similares serem reiniciados.
  5. Verifique a versão em execução, não a imagem que você pretendia implantar.
  6. Durante o rollout: confirme que a regra 3000991 da Akamai (ou o equivalente do seu WAF) e as regras de command injection estão em Deny, trave a origem para aceitar só a borda e rode as regras de multipart primeiro em Alert.
  7. Planeje a migração de fim de vida. Se você está na 8.1 ou anterior, isso deixou de ser tarefa para “algum dia”. Enquanto isso, pergunte ao seu fornecedor sobre um backport.
  8. Verifique plataformas gerenciadas. No Google Cloud, o App Engine standard corrige runtimes suportados automaticamente, mas o App Engine flexible não, e o Cloud Run só atualiza sozinho quando as atualizações automáticas da imagem base estão ativadas (Google Cloud). Outros provedores terão regras próprias; não presuma.
  9. Leia as fontes primárias antes de agir com base no resumo de qualquer pessoa, inclusive este.
